## NODES
1. Every node needs evidence: drawn on the whiteboard (evidencia "visual"), named by the
   speakers as part of the architecture (evidencia "hablada"), or both ("ambas"). Skip
   components mentioned only as rejected alternatives or as the old system. Never add a
   component that neither source contains.
2. "service": exact catalog values. Non-AWS software, databases, SaaS products, and external
   systems are "ThirdParty", with their name in "name". People and client apps take the most
   specific actor type from the actor list.
3. "id": sequential integers as strings ("0", "1", ...).
4. A drawn box and a spoken mention of the same component are ONE node.
5. If the drawing shows a generic group (an "AWS" cloud, "microservices", "analytics") and the
   speakers name the specific services inside it, create one node per named service.
6. Several icons of the same service: fuse them if they act as one logical unit; keep them
   separate if they do distinct steps (e.g. three Lambdas doing different stages).
7. Drop purely physical or decorative concepts. Omit deployment and management layers
   (CloudFormation, CodePipeline, IAM...) unless they take part in the runtime flow.
8. Hosted software (Kafka on EC2, an app on ECS): keep the host only if it is drawn or
   mentioned, and route the application flows to and from the hosted component.
9. "notes": short constraints or metrics stated for that component; "" otherwise.

## EDGES
1. Drawn lines (procedencia "dibujada"): an arrow with one head gives one edge toward the
   head; a line with two heads gives two edges; a line without heads gives one edge whose
   direction comes from the narration or, failing that, from the workflow it belongs to.
2. Spoken flows (procedencia "hablada"): an explicit statement that one component sends,
   calls, triggers, writes to, reads from, publishes to, or streams to another. The component
   that initiates the action is the source. Add the edge only if BOTH ends are nodes.
3. A drawn line and a spoken flow describing the same interaction are ONE edge with
   procedencia "ambas".
4. Direction conflict between a drawn arrowhead and the narration: the drawn arrowhead wins.
5. Returns: edges are unidirectional by default. Add a reverse edge only if it is drawn or
   the speakers explicitly say a response or result flows back.
6. Keep distinct interactions distinct: if the same pair interacts in two different
   workflows, keep one edge per workflow. Do not bypass intermediate nodes.
7. "flow_id": integer per logical workflow, starting at 0. "seq": order within the flow as
   string integers ("0", "1", ...), with a prime (') for parallel steps.
8. "type": "data" for payload transfers, reads and writes; "control" for events, triggers,
   orchestration and asynchronous invocations; "meta" for monitoring, logging, feedback and
   acknowledgements.
9. "respaldo": the evidence — a description of the drawn line and/or a short verbatim quote.
10. Do not use general knowledge about how AWS services usually connect, and do not invent
    an edge just to avoid an isolated node.

Write "razonamiento" briefly, then the graph. "nombre" is a short title for the
architecture. All text in English.
